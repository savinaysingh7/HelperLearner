# HelperLearner From Scratch: Full Reconstruction Manual

This file is meant to be a standalone guide. If you had only this document, you should be able to rebuild a project like this step by step, understand why each part exists, and verify that your rebuild is working.

If you are completely new, read it top to bottom once before you start coding. Then follow the build order exactly.

---

## 1) What This Project Is

HelperLearner is a Django-based web application structured like a real production project. It has:

- A Django project package for core configuration.
- Multiple apps for separated responsibilities.
- Authentication and user-related logic.
- Marketplace-like business logic.
- Notifications and background processing.
- Static files, templates, and media handling.
- Tests, deployment files, and runtime configuration.
- Optional realtime and async support.

The important idea is not just "make pages work." The goal is to build something organized enough that it can grow, be tested, and be deployed safely.

## 7) Start a New Project From Zero

If you were starting from an empty folder, do this first.

### 7.1 Create and activate a virtual environment

```bash
python -m venv venv
```

Windows PowerShell:

```powershell

```

macOS/Linux:

```bash
source venv/bin/activate
```

Upgrade packaging tools:

```bash
python -m pip install --upgrade pip setuptools wheel
```

### 7.2 Install the base dependencies

```bash
pip install django djangorestframework psycopg2-binary celery[redis] redis gunicorn whitenoise python-dotenv pytest pytest-django coverage flake8
```



This creates:

## 8) Settings: The Central Brain of the Project

This is one of the most important parts of the build.

### 8.1 What settings control

Settings control:

- Installed apps.
- Database.
- Static files.
- Templates.
- Authentication.
- Middleware.
- Security.
- Celery.
- Logging.
- Allowed hosts.
- Internationalization.

### 8.2 Recommended approach

For a beginner, you can keep one settings module at first. For a more serious project, split settings into multiple files:

- `base.py`
- `development.py`
- `production.py`

This makes the project easier to reason about.

### 8.3 Core settings you must configure

Add your apps:

```python
INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    'accounts',
    'marketplace',
    'notifications',
    'rest_framework',
]
```

Set templates so Django can find your shared templates:

```python
TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [BASE_DIR / 'templates'],
        'APP_DIRS': True,
        'OPTIONS': {
            'context_processors': [
                'django.template.context_processors.debug',
                'django.template.context_processors.request',
                'django.contrib.auth.context_processors.auth',
                'django.contrib.messages.context_processors.messages',
            ],
        },
    },

```

Set static and media:

```python
STATIC_URL = '/static/'
STATICFILES_DIRS = [BASE_DIR / 'static']
STATIC_ROOT = BASE_DIR / 'staticfiles'

MEDIA_URL = '/media/'
MEDIA_ROOT = BASE_DIR / 'media'
```

Set the custom user model if you create one:

```python
AUTH_USER_MODEL = 'accounts.User'
```

### 8.4 Environment variables

Create `.env` and load it with `python-dotenv` or `django-environ`.


## 9) Database Design: How to Think About the Models

The database is the heart of the app. Before coding views, decide what data exists and how it connects.

### 9.1 Questions to ask first

- Who are the users?
- What can they create?
- What can they request?
- What can they message?
- What gets rated or saved?
- What needs moderation?

### 9.2 Typical model groups in this project

- User / Profile.
- Marketplace listing or request.
- Proposal or application.
- Message / conversation.
- Notification.
- Saved search.
- Rating or trust score.
- Audit / logs / analytics models if needed.

### 9.3 Example custom user model

```python
from django.contrib.auth.models import AbstractUser
from django.db import models


class User(AbstractUser):
    display_name = models.CharField(max_length=150, blank=True)
    bio = models.TextField(blank=True)
    is_verified = models.BooleanField(default=False)

    def __str__(self):
        return self.username
```

### 9.4 Why custom user matters

If you wait too long to customize the user model, it becomes painful to change later. Decide early.

### 9.5 After writing models

Run:

```bash
python manage.py makemigrations
python manage.py migrate
```

Then inspect the generated migration files so you understand what Django is doing.

## 11) URLs: The Routing Map

There are two levels of routing.

### 11.1 Project-level URLs

In `helperlearner_root/urls.py`, include app URLs.

Example:

```python
from django.contrib import admin
from django.urls import path, include
from django.conf import settings
from django.conf.urls.static import static

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('marketplace.urls')),
    path('accounts/', include('accounts.urls')),
    path('notifications/', include('notifications.urls')),
]

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

### 11.2 App-level URLs

Each app gets its own `urls.py`. Keep them small and organized.

### 11.3 Why this matters

Routing is how Django decides which view handles each request. If your URLs are messy, your project becomes hard to navigate.

## 12) Views: How Pages and Actions Actually Work

Views are the functions or classes that handle requests and return responses.

### 12.1 Common view styles

- Function-based views for simple logic.
- Class-based views for reusable patterns.
- DRF views for API responses.

### 12.2 What a view should do

A view should:

1. Read the request.
2. Validate inputs.
3. Fetch or modify data.
4. Choose a response.
5. Return HTML, JSON, redirect, or error.

### 12.3 Keep views small

Do not put huge business logic directly in views. Move business rules into services, query utilities, or model methods when needed.

## 18) Background Tasks with Celery

Celery is used when work should happen after the request finishes.

### 18.1 When to use Celery

- Send email asynchronously.
- Generate reports.
- Process uploads.
- Sync data.
- Expire stale records.

### 18.2 Celery project file

Create `helperlearner_root/celery.py`:

```python
import os
from celery import Celery

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'helperlearner_root.settings')

app = Celery('helperlearner')
app.config_from_object('django.conf:settings', namespace='CELERY')
app.autodiscover_tasks()
```

### 18.3 Celery settings

```python
CELERY_BROKER_URL = env('REDIS_URL')
CELERY_RESULT_BACKEND = env('REDIS_URL')
```

### 18.4 Task files

Put tasks in `tasks.py` inside the app that owns the behavior.

### 18.5 Running Celery locally

```bash
celery -A helperlearner_root worker -l info
```

### 20.1 Why split logic

It keeps code reusable and easier to test.

### 20.2 Good locations for logic

- `services.py` for business operations.
- `tasks.py` for async work.
- `forms.py` for input validation.
- `models.py` for data rules that belong to the model itself.

### 20.3 Example

If multiple pages need the same filter logic, put that logic in a utility function rather than repeating it in every view.

## 29) Docker: Make the Project Reproducible

### 29.2 Minimal `Dockerfile`

```dockerfile
ENV PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y --no-install-recommends build-essential && rm -rf /var/lib/apt/lists/*
```

**Tag Model** (Categorization with slug):
```python
class Tag(models.Model):
    name = models.CharField(max_length=50, unique=True)
    slug = models.SlugField(max_length=60, unique=True, blank=True)
    
    def save(self, *args, **kwargs):
        """Slugify tag names and enforce unique slugs."""
        base_slug = slugify(self.name) or 'tag'
        slug = base_slug
        counter = 2
        while Tag.objects.filter(slug=slug).exclude(pk=self.pk).exists():
            slug = f'{base_slug}-{counter}'
            counter += 1
        self.slug = slug
        super().save(*args, **kwargs)
```
- **Purpose:** User-friendly URL-safe identifiers for filtering searches
- **Slug Logic:** Auto-generates slug from name; handles collisions with counter (tag-2, tag-3)

```python
def unified_search(request):
    """
    Search requests and jobs by keyword using PostgreSQL full-text search.
    Falls back to LIKE search for non-PostgreSQL databases.
    """
    query = request.GET.get('q', '').strip()
    skill_id = request.GET.get('skill_id')
    tag_id = request.GET.get('tag_id')
    
    requests_qs = HelpRequest.objects.filter(status='open')
    jobs_qs = FreelanceJob.objects.filter(status='open')
    
    if query:
        from django.contrib.postgres.search import SearchVector, SearchQuery, SearchRank
        
        search_vector = SearchVector('title', weight='A') + SearchVector('description', weight='B')
        search_query = SearchQuery(query, search_type='websearch')
        
        requests_qs = requests_qs.annotate(
            search=search_vector,
            rank=SearchRank(search_vector, search_query)
        ).filter(search=search_query).order_by('-rank')
        
        jobs_qs = jobs_qs.annotate(
            search=search_vector,
            rank=SearchRank(search_vector, search_query)
        ).filter(search=search_query).order_by('-rank')
    
    if skill_id:
        requests_qs = requests_qs.filter(skill_needed_id=skill_id)
        jobs_qs = jobs_qs.filter(skill_needed_id=skill_id)
    
    if tag_id:
        requests_qs = requests_qs.filter(tags__id=tag_id)
        jobs_qs = jobs_qs.filter(tags__id=tag_id)
    
    return render(request, 'marketplace/search_results.html', {
        'requests': requests_qs[:20],
        'jobs': jobs_qs[:20],
    })
```
- **PostgreSQL Full-Text Search:** Uses SearchVector/SearchQuery for relevance ranking
- **Fallback:** If not using PostgreSQL, can fall back to LIKE search
- **Filters:** Can filter by skill or tag in addition to keyword search

```python
@transaction.atomic
def claim_help_request(request, pk):
    """
    Helper claims a help request and is deducted KP.
    Must have accepted_by=None (not yet claimed).
    """
    help_req = HelpRequest.objects.select_for_update().get(pk=pk)
    
    if help_req.accepted_by is not None:
        raise ValidationError('Request already claimed by someone.')
    
    if help_req.status != 'open':
        raise ValidationError('Can only claim open requests.')
    
    user = request.user
    
    # Deduct KP from user wallet
    if user.kp < help_req.kp_bounty:
        raise ValidationError('Insufficient KP to claim this request.')
    
    # Update user KP (subtract bounty as escrow)
    user.kp -= help_req.kp_bounty
    user.save(update_fields=['kp'])
    
    # Update request status
    help_req.accepted_by = user
    help_req.status = 'in_progress'
    help_req.save(update_fields=['accepted_by', 'status'])
    
    # Signal: invalidate_home_cache
    # Sends notification to requester: "Your request claimed by X"
    
    return JsonResponse({'status': 'claimed'})
```
- **Atomic Transaction:** select_for_update() prevents race conditions (two helpers claiming same request)
- **KP Deduction:** Helper KP reduced immediately (acts as escrow)
- **Status Change:** Request moves to in_progress
- **Signals:** Cache invalidated, notification sent

```python
def razorpay_webhook(request):
    """
    Razorpay calls this endpoint with payment success/failure.
    Verify signature and update milestone status.
    """
    import razorpay
    
    if request.method != 'POST':
        return JsonResponse({'status': 'error'}, status=400)
    
    data = json.loads(request.body)
    
    # Verify signature
    razorpay_client = razorpay.Client(
        auth=(settings.RAZORPAY_KEY_ID, settings.RAZORPAY_KEY_SECRET)
    )
    
    try:
        razorpay_client.utility.verify_webhook_signature(
            data,
            settings.RAZORPAY_WEBHOOK_SECRET
        )
    except razorpay.errors.SignatureVerificationError:
        return JsonResponse({'status': 'error', 'message': 'Invalid signature'}, status=400)
    
    if data['event'] == 'payment.authorized':
        payment_data = data['payload']['payment']['entity']
        order_id = payment_data['order_id']
        
        # Find milestone by order receipt
        order = razorpay_client.order.fetch(order_id)
        milestone_id = order['notes']['milestone_id']
        
        milestone = JobMilestone.objects.get(pk=milestone_id)
        milestone.status = 'funded'
        milestone.save(update_fields=['status'])
        
        # Debit client wallet for funded amount
        job = milestone.job
        job.client.wallet_inr -= milestone.amount_inr
        job.client.save(update_fields=['wallet_inr'])
        
        # Log ledger
        WalletLedger.objects.create(
            user=job.client,
            direction='debit',
            amount_inr=milestone.amount_inr,
            source_type='milestone_funding',
            reference_id=milestone.pk,
        )
        
        return JsonResponse({'status': 'success'})
    
    return JsonResponse({'status': 'ignored'})
```

```python
@shared_task(bind=True, max_retries=5)
def send_templated_email_task(self, template_slug, to_email, context, **kwargs):
    """
    Send templated email via SMTP.
    Retry with exponential backoff on failure.
    """
    try:
        from django.template.loader import render_to_string
        
        # Load email template
        html_message = render_to_string(
            f'emails/{template_slug}.html',
            context
        )
        subject = f'HelperLearner: {context.get("subject", "Update")}'
        
        # Send via configured email backend
        send_mail(
            subject=subject,
            message='',  # Plain text version
            from_email=settings.DEFAULT_FROM_EMAIL,
            recipient_list=[to_email],
            html_message=html_message,
            fail_silently=False,
        )
        
        return f'Email sent to {to_email}'
    
    except Exception as exc:
        # Exponential backoff: 2^retry_count seconds
        retry_delay = 2 ** self.request.retries
        raise self.retry(exc=exc, countdown=retry_delay)
```
- **Template Rendering:** HTML email generated server-side
- **Exponential Backoff:** First retry at 2s, then 4s, 8s, 16s, 32s
- **Max Retries:** 5 attempts before giving up
- **Graceful Degradation:** fail_silently=False to surface errors

### Transactional Safety Pattern:

```python
@transaction.atomic
def debit_and_credit_wallets(payer, payee, amount_inr):
    """
    Safely transfer funds between two wallets.
    If any step fails, entire transaction rolls back.
    """
    payer_obj = User.objects.select_for_update().get(pk=payer.pk)
    payee_obj = User.objects.select_for_update().get(pk=payee.pk)
    
    if payer_obj.wallet_inr < amount_inr:
        raise ValidationError('Insufficient balance.')
    
    payer_obj.wallet_inr -= amount_inr
    payee_obj.wallet_inr += amount_inr
    
    payer_obj.save(update_fields=['wallet_inr'])
    payee_obj.save(update_fields=['wallet_inr'])
    
    # Log both debits and credits
    WalletLedger.objects.bulk_create([
        WalletLedger(
            user=payer_obj,
            direction='debit',
            amount_inr=amount_inr,
            source_type='transfer',
        ),
        WalletLedger(
            user=payee_obj,
            direction='credit',
            amount_inr=amount_inr,
            source_type='transfer',
        ),
    ])
```

## 42) Python File Reference: What Every File Does

### 42.1 Top-level project files

- `manage.py` starts Django commands. It sets the default settings module to `helperlearner_root.settings.dev`, imports Django's command runner, and forwards CLI arguments to it. This is the file you use for migrations, tests, shell, runserver, and custom commands.

### 42.2 Project package: `helperlearner_root/`

- `helperlearner_root/__init__.py` initializes the project package and exposes `celery_app` if Celery is available. This lets the Django app and worker process share the same Celery bootstrap.

- `helperlearner_root/wsgi.py` is the WSGI entry point for traditional production servers like Gunicorn. It reads `DJANGO_SETTINGS_MODULE` from the environment or defaults to the dev settings module, then exposes `application`.
- `helperlearner_root/celery.py` bootstraps Celery. It reads the settings module from `DJANGO_SETTINGS_MODULE`, builds `celery_app`, configures it from Django settings, and autodiscovers tasks.

- `helperlearner_root/logging_context.py` adds request-scoped logging context. It exposes `set_request_context`, `update_request_user`, `reset_request_context`, and a `RequestContextFilter` to enrich logs with request details.

### 42.10 What to learn from the code layout

- User-facing pages live in `views.py` and `advanced_views.py`.

- Configuration lives in `settings/`.

That separation is the real reason the project is maintainable.

If you rebuild the code but these tests fail, the rebuild is not complete.

## 44) Core File Walkthrough: Code-Level Explanation of the Biggest Python Files

This section is the closest thing to a guided reading of the code itself. For very large files, the best way to explain the code is by section and responsibility, because a literal line-by-line dump would be unreadable. The point here is to understand what each block of code does and why it exists.

### 44.1 `helperlearner_root/settings/base.py`

This file is the configuration center of the whole app.

- The imports at the top bring in logging, path handling, `sys`, `dj_database_url`, `decouple.config`, and `ImproperlyConfigured`. That tells you the file is meant to read environment variables, manage filesystem paths, and validate deployment safety.
- `BASE_DIR` points to the root of the repository. Other paths are built from it.
- `TESTING = 'test' in sys.argv` is a quick flag to detect test runs.
- `logger = logging.getLogger(__name__)` lets the settings file emit warnings when something is misconfigured.
- `LOG_FILE_PATH` reads the log path from environment or defaults to `logs/server.log`. The directory is created if it does not exist.
- `env_bool()` is a helper that safely converts environment strings into real booleans. It accepts values like `true`, `yes`, `1`, `on`, and rejects invalid values by logging a warning and falling back to a default. This protects production startup from bad env values.
- `SECRET_KEY` is read from the environment. The code refuses to continue in production if it is still the unsafe dev placeholder.
- `DEBUG` is also read through `env_bool()`. This is important because environment strings are not automatically booleans.
- `ALLOWED_HOSTS` is read from the environment and split into a clean list.
- `RENDER_EXTERNAL_HOSTNAME` is appended when present. This is specific to Render deployments.
- `INSTALLED_APPS` registers Django core apps plus `rest_framework`, `django_filters`, `axes`, and the local apps `accounts`, `marketplace`, and `notifications`.
- `MIDDLEWARE` sets the request-processing chain. Security, WhiteNoise, sessions, request metrics, CSRF, authentication, experiment assignment, suspension enforcement, Axes, messaging, and clickjacking protection all happen here in order.
- `ROOT_URLCONF` points to the main URL router in `helperlearner_root.urls`.
- `TEMPLATES` tells Django where to find HTML files and which context processors inject global data into templates. The extra processors for notifications and marketplace features are how those values appear in every page.
- `WSGI_APPLICATION` points to the production WSGI entry point.
- The `try`/`except` around `channels` makes websocket support optional. If Channels is installed, `HAS_CHANNELS` is `True`, `channels` is added to `INSTALLED_APPS`, and `ASGI_APPLICATION` is set. Otherwise ASGI still exists but without Channels-specific layers.
- `CHANNEL_LAYERS` uses an in-memory backend when Channels is active. That is simple for local use but not ideal for scaling; Redis would be the production choice.
- `DATABASES` uses `dj_database_url.config()` so the app can read a single `DATABASE_URL` string instead of building database settings manually.
- `AUTH_PASSWORD_VALIDATORS` keeps Django’s standard password quality checks enabled.
- `AUTHENTICATION_BACKENDS` puts Axes first so brute-force protection works alongside Django’s standard backend.
- `REST_FRAMEWORK` configures API pagination, filtering, and authentication. The custom `ApiKeyAuthentication` means some endpoints can use API keys in addition to session auth.
- `REDIS_URL`, `CACHE_LOCATION`, and `CACHE_BACKEND` control cache selection. If Redis is available and `django-redis` is installed, the cache uses Redis; otherwise it falls back to local memory.
- `LANGUAGE_CODE`, `TIME_ZONE`, `USE_I18N`, and `USE_TZ` define locale handling.
- `STATIC_URL`, `STATIC_ROOT`, `STATICFILES_DIRS`, and `STATICFILES_STORAGE` define how static assets are collected and served. WhiteNoise is used for compressed manifest-based serving.
- `MEDIA_URL` and `MEDIA_ROOT` define uploaded file storage.
- `AUTH_USER_MODEL = 'accounts.CustomUser'` is crucial. It tells Django to use the custom user model from the `accounts` app.
- `LOGIN_REDIRECT_URL` and `LOGOUT_REDIRECT_URL` control where authenticated users go after login/logout.
- `DEFAULT_FROM_EMAIL`, `GEMINI_API_KEY`, `GEMINI_MODEL`, and the AI timeout/cache toggles support email and AI features.
- The second `REST_FRAMEWORK` block refines API auth and throttling. This means API behavior is intentionally rate limited and secured.
- `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, and `RAZORPAY_WEBHOOK_SECRET` configure payments.
- `AI_SUMMARY_CACHE_SECONDS`, `PUBLIC_STATS_CACHE_SECONDS`, and `SLOW_REQUEST_THRESHOLD_MS` tune performance and observability.
- `READINESS_CHECK_CELERY` and `READINESS_CHECK_CELERY_TIMEOUT_SECONDS` control whether readiness checks should probe Celery.
- The remaining constants configure webhook retries, notification toggles, KP economics, Sentry, security hardening, Axes lockout behavior, and logging.

In plain English: this file wires the whole system together, decides which environment it is running in, and protects the app from unsafe startup states.

### 44.2 `accounts/models.py`

This file defines the user account data model.

- `CustomUser(AbstractUser)` extends Django’s default user with project-specific fields.
- `NotificationPreference` stores whether the user wants in-app notifications, email notifications, both, or none.
- `UiDensity` stores whether the interface should look comfortable or compact.
- `bio` gives the user a profile description.
- `knowledge_points` is the gamification currency used throughout the platform.
- `last_kp_claim` stores when the user last claimed daily KP.
- `skills` is a many-to-many relation to marketplace skills. This is why user profiles can be matched to requests.
- `wallet_inr` stores real-money wallet value.
- `compliance_verified`, `is_suspended`, `suspended_until`, and `suspension_reason` support trust and moderation.
- `notification_preference` and `ui_density` store user-facing preferences.
- `trust_score` and `trust_score_updated_at` support trust-based ranking and profile display.
- The `notify_*` fields are more granular topic preferences for requests, jobs, chat, and KP.
- `allows_in_app_notifications()` and `allows_email_notifications()` are convenience checks used throughout notification logic.
- `is_currently_suspended()` decides whether a suspension still applies based on the current time.
- `trust_signal_score` aggregates related trust signal records so the app can compute a user’s trust from historical events.
- `Meta` sets ordering and adds indexes for the fields the app queries often.
- The `CheckConstraint`s make sure KP and wallet balances cannot go negative at the database level.
- `AuditLog` stores administrative and system events. It links to the user who acted, the target user, the action name, IP address, arbitrary metadata, and the creation time.

In plain English: this file defines who a user is, what they are allowed to prefer, how much they own, and how trustworthy or suspended they are.

### 44.3 `accounts/views.py`

This file turns account data into user-facing actions.

- `_profile_queryset()` returns annotated users with rating data and prefetched skills. This keeps profile pages and public profiles efficient.
- `_month_start()` computes the first day of a month N months before a reference time. The dashboard uses this to build monthly charts.
- `_next_bonus_hours()` calculates how long until the next KP claim becomes available.
- `signup()` handles registration. On `POST` it validates `DeveloperSignUpForm`, saves the new user, logs them in, and redirects home. On `GET` it renders the signup form.
- `profile()` shows the logged-in user their profile page, including their own requests and tasks.
- `public_profile()` shows another user’s profile, including posted count, helped count, and portfolio items.
- `edit_profile()` lets the logged-in user update profile fields, skills, and notification preferences. It logs the change with `log_event()` and records the client IP.
- `dashboard()` computes the most important account metrics: KP earned and spent, requests posted and helped, success rate, average rating, pending proposals, open disputes, unread notifications, activity trends over six months, and paid-job totals. This function is one of the most analytics-heavy pieces of the account app.

In plain English: this file handles account creation, profile management, dashboards, and KP-related user actions.

### 44.4 `marketplace/models.py`

This is the largest data file in the project, so it is best understood as a set of business entities grouped by purpose.

- `Skill` is a simple named capability used for matching.
- `Tag` stores searchable labels. Its custom `save()` method slugifies names and ensures slugs stay unique.
- `HelpRequest` is the main help-seeking record. It stores title, description, owner, required skill, tags, KP bounty, status, summary, timestamps, expiry, and accepted helper. Its `save()` method auto-fills expiry if needed.
- `HelpRequestProposal` is an application from a helper to solve a request. Its `clean()` method blocks self-proposals and proposals above the bounty.
- `Comment` stores discussion under a request, including whether the comment is private.
- `Rating` stores one rating per request from the requester to the helper.
- `SavedSearch` stores a reusable request-search filter. Its `clean()` method requires at least one criterion, and its `save()` trims whitespace.
- `FreelanceJob` is the paid-work version of the marketplace. It stores title, description, client, freelancer, skill, tags, payment type, budget, escrow, status, fee waiver, deadline, response SLA, and lifecycle timestamps. Its `clean()` and `save()` logic later in the file coordinate business rules around funding and deadlines.
- `FreelanceJobProposal` stores proposal applications for jobs.
- `FreelanceJobProposalMilestone` links proposal milestones to job work plans.
- `JobMilestone` stores the breakdown of work under a freelance job.
- `JobDispute` tracks conflicts about paid work.
- `WalletLedger` records wallet movements.
- `PayoutRequest` stores a request to withdraw money.
- `TrustSignal` stores trust-related positive or negative events.
- `MilestoneDeliverable` stores submitted work artifacts.
- `Attachment` stores uploaded files.
- `FraudAlert` stores suspicious activity reports.
- `KPTransfer` stores one KP transfer between users.
- `KPPerkPurchase` stores a KP-based purchase of a perk like proposal highlighting or fee waiver.
- `Workspace`, `WorkspaceMembership`, `WorkspaceWalletEntry`, `WorkspaceProject`, `WorkspaceIssue`, `WorkspaceIssueActivity`, `WorkspaceSprint`, and `WorkspaceIssueComment` support collaborative workspace and sprint workflows.
- `ChatThread`, `ChatThreadParticipant`, and `ChatMessage` support direct or workspace chat.
- `PortfolioItem` stores portfolio entries.
- `IntegrationApiKey` stores API keys and hashing logic.
- `WebhookEndpoint` and `WebhookDelivery` store outbound integration targets and delivery history.
- `ModerationFlag` stores content moderation reports.
- `Experiment`, `ExperimentVariant`, and `ExperimentAssignment` support feature flags and experiments.

The `Meta` classes throughout this file are not decorative. They define ordering, database indexes, and unique constraints so common queries stay fast and the data stays valid.

In plain English: this file defines almost every object the platform cares about. The rest of the project mostly reads, writes, validates, or reacts to these models.

### 44.5 `marketplace/views.py`

This file is the main behavior layer for the public product.

- `kp_marketplace()` shows available KP perks.
- `purchase_perk()` deducts KP and creates an active perk purchase inside a transaction. The `select_for_update()` call prevents race conditions when multiple purchases happen at once.
- `_cache_get_or_set()` wraps cache reads and writes.
- `_ordered_by_ids()` reorders query results to match a precomputed id sequence. This keeps ranking and cached order stable.
- `home()` builds homepage stats and recent open requests/jobs, using cached counts to avoid expensive repeated queries.
- `_search_querysets()` performs grouped search across requests, users, and skills, with PostgreSQL full-text search when available and fallback `icontains` matching otherwise.
- The remaining helpers around saved searches, ordering, and notifications help the page-level views stay smaller.

The rest of this file follows the same pattern:

- request browsing and creation,
- proposal submission and selection,
- claim/resolve/cancel lifecycle,
- freelance job creation and management,
- milestone submission and release,
- dispute opening,
- wallet/ledger exports,
- search, saved searches, activity feed, and leaderboard.

The viewsets at the end expose API-readable versions of the data.

In plain English: this file is the app’s interactive surface. It takes user actions and turns them into model changes, notifications, wallet effects, and rendered pages.

### 44.6 `notifications/signals.py`

This file reacts automatically when other models change.

- `_send_notification_email()` is a safe wrapper around email sending.
- `cache_previous_status()` runs before a `HelpRequest` save so the system can detect whether the status changed.
- `create_help_request_notifications()` is the main notification reaction. It looks at the previous and current request status and decides whether to create an in-app notification and/or send email to the poster or helper.
- `push_realtime_notification()` forwards new notifications to websocket clients by calling `emit_user_event()`.

In plain English: this file is the automation layer that keeps notifications and realtime updates in sync with core marketplace changes.

### 44.7 `notifications/tasks.py`

This file moves email sending into background jobs.

- `shared_task` is imported from Celery if available; otherwise a no-op fallback is defined so the code can still import safely.
- `send_templated_email_task()` is a retryable Celery task. It sends a templated email, retries transient failures, and returns a small status payload.

In plain English: this file prevents email delivery from slowing down user requests.

### 44.8 `helperlearner_root/views.py`

This file exposes the app-level operational endpoints.

- `_check_database()` opens a DB cursor and runs `SELECT 1` to prove the database can answer queries.
- `_check_cache()` writes and reads a small probe key to verify the cache is functional.
- `_check_celery_broker()` attempts to connect to the Celery broker using Kombu, if readiness checks require it.
- `health_check()` returns a lightweight JSON response for load balancers and uptime monitoring.
- `readiness_check()` performs the full readiness probe and returns `ready` or `degraded` with per-check status and error messages.
- `service_worker()` serves the PWA service worker file from the static files finder and sets the `Service-Worker-Allowed` header so it can operate from the root scope.

In plain English: this file is what lets infrastructure know whether the app is alive, ready, and serving its PWA assets correctly.

### 44.9 Management commands and background scripts

- `marketplace/management/commands/diagnose_runtime.py` runs operational diagnostics.
- `seed_indian_demo_data.py` builds a full demo dataset with users, requests, jobs, workspaces, chat, moderation data, KP transfers, attachments, deliverables, and experiments.
- `run_sla_engine.py` drives SLA automation.

In plain English: these files automate things you would not want to do by hand after every deploy.

### 44.10 How to read any other file in the repo

When you open a new Python file, ask these questions:

1. Is it defining data? Then it is probably a model.
2. Is it accepting user input? Then it is probably a form or view.
3. Is it reacting to changes? Then it is probably a signal.
4. Is it doing repeated background work? Then it is probably a task or command.
5. Is it wiring startup behavior? Then it is probably settings, WSGI, ASGI, middleware, or runtime checks.

That is the fastest way to understand unfamiliar code in this project.
